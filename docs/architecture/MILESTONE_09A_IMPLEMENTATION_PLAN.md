## Migration discipline

Use a disposable PostgreSQL instance for migration tests only **after** separate 09A.2 implementation authorization. Generate/review EF Core migrations against the approved four-table SQL design and guard triggers, then apply by an operator/deployment process with a separate migration credential; do not call `Migrate()` during ordinary API startup. The existing `ashenfall_app` role currently has CONNECT only; an authorized future migration may grant it `USAGE` on `public` plus `SELECT` on the four catalog tables, never DDL or publication writes. A distinct trusted publisher identity/administrative operation handles draft writes and publication; its exact identity is an owner decision. Preserve older catalog releases while persistent characters or running encounters reference them. Seed catalog publication is one transaction: serialize publishers, validate all rows and the canonical content hash, retire the previous active release, publish the new release, then commit. A versioned snapshot read uses one `REPEATABLE READ READ ONLY` transaction so release metadata and definition rows come from one MVCC view. Pinning prevents a balance update from changing an active attack. [EF Core's migration overview](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/) and [PostgreSQL row-lock guidance](https://www.postgresql.org/docs/current/explicit-locking.html) inform the plan.

## Security and integrity gates

| Risk | Proportionate gate |
| --- | --- |
| DB credentials in game build | Backend-only secret store/environment; inspect build artifacts for connection strings; database firewall/private access |
| Unauthorized character read/write | No character endpoint until auth; derive account from validated claims, enforce owner check, private responses `no-store` |
| Two simultaneous character creations | Lock account row and count active characters in one DB transaction; backend configurable limit 1; concurrency test |
| Client-supplied stats/hits/exploration | Ignore for persistence/host simulation; future host loads catalog and validates commands/line of sight; client remains prototype-authoritative only until then |
| Invalid equipment or progression | API transaction validates owned item, slot/category, class/level rules and available points; DB FKs/checks and revision guard supplement it |
| Catalog mismatch or partial rollout | Immutable release, `schemaMajor`, content hash, atomic snapshot, previous-version retention and encounter pinning |
| Concurrent updates | Explicit `row_revision` compare-and-increment and 409 conflicts; short transactions; reviewed retry policy |
| Development fallback leaking into production | Explicit Development-only switch; production startup fails if enabled; no private state access without authentication |

## Decisions required before 09A.2

1. Choose the minimum supported PostgreSQL major and the approved migration owner/deployment process. The proposal avoids version-specific UUID-generation defaults.
2. Confirm that public catalog reads may be unauthenticated, while all future mutable account/character routes wait for an identity provider and authorization model.
3. Approve four immediate catalog tables and seven deferred tables, including `hand_requirement` on weapons, publication guards, no row per temporary enemy and compact exploration masks.
4. Confirm whether the first online production client must fail startup without the API or may offer a separately labeled, truly offline single-player mode. Development fallback must never become a production auth bypass.
5. Confirm whether character names are unique **per account** (proposed) and how old catalog releases are retained for saved characters.
6. Approve the first cutover's explicit scene override policy: base Guardian windup 600 ms, first-adventure windup 1200 ms, West/East detection/leash overrides retained.
